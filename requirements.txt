You are the lead graphics-engine architect and senior C/Vulkan developer for this project.

The project name is **Arcflow**.

Build a native application for authoring and playing:

1. High-performance 2D vector UI animations
2. Interactive game-interface animations
3. Real-time particles and visual effects
4. Lightweight animations embeddable into custom game engines

The product is conceptually similar to a focused combination of a vector-animation editor, UI animation state-machine editor, and game VFX authoring tool.

Do not attempt to reproduce every feature of existing commercial tools.

The primary goals are:

* Predictable performance
* Low runtime overhead
* Small compiled assets
* Resolution-independent UI
* Flexible animation authoring
* Deterministic playback
* Safe loading of untrusted assets
* Clean integration into Vulkan game engines
* A maintainable C codebase

Implement the system incrementally.

Only implement the active milestone. Do not implement future features prematurely.

# 7. Renderer design

Implement one renderer backend only:

```text
Vulkan 1.3
```

Maintain a clean boundary between scene systems and Vulkan code, but do not create a large theoretical multi-backend abstraction.

The scene and animation systems should generate backend-neutral render commands such as:

* Draw analytic shape instances
* Draw vector meshes
* Draw image instances
* Draw text glyph instances
* Begin clipping region
* End clipping region
* Begin offscreen layer
* Composite offscreen layer
* Dispatch particle simulation
* Draw particle batch

Only the renderer module may directly access Vulkan objects.

Do not expose these outside the renderer:

* `VkBuffer`
* `VkImage`
* `VkPipeline`
* `VkDescriptorSet`
* Vulkan barriers
* Vulkan memory allocations

The public Arcflow Runtime integration API may accept host-owned Vulkan objects, but internal scene nodes must remain independent from Vulkan handles.

# 8. Vector rendering strategy

Use a hybrid vector-rendering approach.

## Analytic GPU primitives

Render these using instanced quads and fragment-shader distance calculations:

* Rectangle
* Rounded rectangle
* Ellipse
* Circle
* Line segment
* Simple border
* Solid fill
* Basic linear gradient
* Basic radial gradient

These primitives must not require CPU tessellation.

Instance data should contain only required values such as:

* Transform
* Bounds
* Fill parameters
* Border parameters
* Gradient parameters
* Opacity
* Clip identifier
* Layer order

Batch compatible analytic primitives.

Avoid one draw call per shape.

## Tessellated vector paths

Use tessellation for:

* Arbitrary Bézier paths
* Complex polygons
* Complex strokes
* Nontrivial fill rules
* Trimmed paths
* Paths used as particle-emission sources

Begin with CPU path flattening and CPU tessellation.

Place tessellation behind a replaceable internal interface.

Do not build GPU tessellation in early milestones.

## Geometry caching

Every path must have separate generation counters for:

* Geometry
* Paint
* Transform
* Animation data

Only rebuild path geometry when geometry-affecting properties change.

Changing these properties must not trigger tessellation:

* Position
* Rotation
* Scale
* Opacity
* Solid fill color
* Layer visibility

Use cached GPU geometry for unchanged paths.

Track geometry-cache memory and add eviction policies later.

# 16. Runtime API rules

Expose an opaque C API.

The host must be able to:

* Create an Arcflow runtime context
* Supply an existing Vulkan instance
* Supply a physical device
* Supply a logical device
* Supply queue information
* Supply command buffers
* Load a package from memory
* Create an animation instance
* Destroy an instance
* Set animation time
* Play or stop an animation
* Set playback speed
* Set exposed numeric properties
* Set runtime text
* Resize the canvas
* Supply safe-area information
* Update an instance
* Poll animation events
* Record rendering commands

Do not automatically submit command buffers by default.

Do not automatically call `vkDeviceWaitIdle`.

Do not create a second Vulkan device.

Clearly define:

* Host ownership
* Runtime ownership
* Required image layouts
* Synchronization responsibilities
* Frames-in-flight requirements
* Destruction order

Use generation-based runtime handles.

Reject stale handles safely.

Example public API shape:

```c
#ifndef ARCFLOW_RUNTIME_H
#define ARCFLOW_RUNTIME_H

#include <stddef.h>
#include <stdint.h>
#include <vulkan/vulkan.h>

typedef struct AfRuntime AfRuntime;

typedef uint64_t AfPackageHandle;
typedef uint64_t AfInstanceHandle;

typedef enum AfResult {
    AF_RESULT_SUCCESS = 0,
    AF_RESULT_INVALID_ARGUMENT,
    AF_RESULT_OUT_OF_MEMORY,
    AF_RESULT_INVALID_PACKAGE,
    AF_RESULT_UNSUPPORTED_FEATURE,
    AF_RESULT_STALE_HANDLE,
    AF_RESULT_VULKAN_ERROR
} AfResult;

typedef struct AfRuntimeCreateInfo {
    VkInstance instance;
    VkPhysicalDevice physical_device;
    VkDevice device;

    VkQueue graphics_queue;
    uint32_t graphics_queue_family;

    uint32_t frames_in_flight;
} AfRuntimeCreateInfo;

AfResult af_runtime_create(
    const AfRuntimeCreateInfo *create_info,
    AfRuntime **out_runtime
);

void af_runtime_destroy(AfRuntime *runtime);

AfResult af_package_load(
    AfRuntime *runtime,
    const void *data,
    size_t data_size,
    AfPackageHandle *out_package
);

AfResult af_package_destroy(
    AfRuntime *runtime,
    AfPackageHandle package
);

AfResult af_instance_create(
    AfRuntime *runtime,
    AfPackageHandle package,
    AfInstanceHandle *out_instance
);

AfResult af_instance_destroy(
    AfRuntime *runtime,
    AfInstanceHandle instance
);

AfResult af_instance_update(
    AfRuntime *runtime,
    AfInstanceHandle instance,
    float delta_time
);

#endif
```

The exact API may evolve, but public ownership and error behavior must remain explicit.

# 17. Runtime package format

Call the compiled format the:

```text
Arcflow Runtime Package
```

Use a stable file extension such as:

```text
.afp
```

Do not assume the extension provides security or validation.

Every package must include:

* Magic bytes
* Format version
* Minimum runtime version
* Endianness marker
* Total file size
* Section-table offset
* Section count
* Required-feature flags
* Optional checksum

Use Arcflow-specific package magic.

For example, define the magic through explicit bytes rather than relying on implementation-defined multi-character literals:

```c
static const uint8_t AF_PACKAGE_MAGIC[8] = {
    'A', 'R', 'C', 'F', 'L', 'O', 'W', '\0'
};
```

Every section must include:

* Type
* Offset
* Size
* Alignment
* Element count where applicable

Before reading any value:

* Check integer addition overflow
* Check integer multiplication overflow
* Check offset bounds
* Check size bounds
* Check alignment
* Check element-count limits
* Check section-overlap rules
* Check reference validity

Do not cast package memory directly to arbitrary C structures unless alignment, size, endianness, and representation have been explicitly validated.

Prefer decoding fixed-width fields through safe-reader functions.

Create a package-validation function that does not create GPU resources.

The package validator must be suitable for fuzz testing.
